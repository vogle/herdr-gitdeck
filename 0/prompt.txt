## Conclusions to put in the report (my analysis so far)
- Q1: A Herdr mod proper must be JS (`main.js`) describing gpui-kit elements. No WASM or native-plugin loading is documented, and `WebAssembly` is undefined in herdr-app 0.1.15. Rust or Go can only be a helper binary launched through `exec` (supported, trusted, 30 s default and 10 min cap, no stdin). The UI stays in JS.
- Q2: Rust and Go mods are a small minority (about 2.6% and 2.2% of the topic), and JS dominates. The Rust/Go examples (herdr-gitview, auto-title) use the pattern "JS UI wrapper plus an engine binary via exec, delivered as prebuilt per-OS releases with SHA-256". Some Rust and Go repos are TUI plugins, a different system.
- Q3, factors to weigh:
  - Performance: git commands dominate, so the language of the wrapper barely matters. Process spawn costs and the exec limits are the same either way.
  - Distribution: TypeScript ships one 202 KB JS file with no per-OS builds. Rust or Go needs per-OS/arch binaries, a release matrix, checksums and glibc compatibility, and still leaves the JS UI layer.
  - Auto-update: the current updater swaps a tarball of JS and assets with `herdr-app check`. A binary would add download, verification and permission handling, and would break the single-rename swap model.
  - Tests: 326 tests at 99.7% line coverage would have to be rewritten or duplicated (a split between a Rust engine and the JS UI means two test systems).
  - Migration effort: the 7,348-line core and its tests would need porting (guess, not measured).
  - Security: JS mods and binaries are both trusted code. A binary adds supply-chain surface (downloaded executables), while the current tarball contains only readable JS.
- Q4 leaning recommendation: stay with TypeScript. Revisit a Rust helper only if a measured need appears, such as heavy parsing or a graph over huge repos.
